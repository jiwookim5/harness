# techniques-sweep

`techniques.md`에 정리된 공격 기법을 순서대로 소진하고, 전부 실패하면 무작정 반복하는 대신 **사람이 방향을 정하고 AI는 그 안에서 실행**하는 절차. AGENTS.md의 "무제한 자동화 금지" / "새로운 Target·명령 범주 추가 시 개별 GO 필요" / "AI는 Scope를 승인하지 않는다" 조항을 지키기 위한 구조.

## 역할 분리 (이 스킬 전체에 적용되는 원칙)

| 영역 | 누가 결정하는가 |
|---|---|
| 이번 세션에서 어느 영역/기능을 우선 팔지 (비즈니스 스코프) | **사람** — 실제 세상 맥락(리스크, 보상, 관심사)은 AI가 모름 |
| 다 실패했을 때 어느 방향으로 다시 팔지 (기술적 triage) | **AI가 의견 제시 + 사람이 최종 선택** — AI는 raw 데이터와 근거 있는 의견을 같이 보여주되, 사람이 언제든 다른 방향으로 뒤집을 수 있게 열어둠 |
| 무엇이 진짜 취약점인지 최종 확정 | **사람** — AI는 "대기중"까지만 |
| Control 실행, 로그 남기기, 파일 정리, recon.md 기록, 기술적 우선순위 triage | **AI** — 사람이 매번 반복할 필요 없는 손 노동 + 분석 |

AI가 "이렇게 할까요?"라는 예/아니오 질문 하나로 방향을 확정 지어버리면 안 된다. 의견은 내되, 근거를 밝히고, 사람이 다른 방향을 고를 수 있는 여지를 항상 남긴다. **비즈니스 스코프(어디가 중요한가)는 AI가 절대 먼저 정하지 않고, 기술적 triage(뭐가 더 유력한가)는 AI가 의견을 내도 되지만 결정권은 사람에게 있다.**

## 0. Preflight (매번 먼저 확인)

- `scope.md`의 Scope 승인 상태 확인. PENDING이면 **실제 Control 실행 중단**, 사람에게 승인 상태부터 확인받는다. (정적 분석/문서 정리는 계속해도 됨)
- `git status`로 이전 세션 잔여물 확인.
- 이 스킬이 다루는 대상 파일: `techniques.md`(공격 목록), `recon.md`(시도 기록), `finding-summary.md`(확정된 취약점 요약), `retrospective/`(재현검증+근본원인), `report.md`(최종 보고서).
- **재현성 고정 (재작업 방지)**: 분석 대상 APK/앱 버전의 식별자(파일 hash 또는 버전 번호)와 사용한 주요 도구 버전을 `recon.md` 상단에 기록해둔다. 나중에 "이거 그때 그 버전 맞나?" 확인하느라 다시 조사하는 시간을 아끼기 위함 — 속도 자체보다 재작업 방지가 목적.

## 0.5 탐색적 Recon (가설 없는 정찰) — techniques.md 밖의 취약점 대비

techniques.md는 결국 "알려진 취약점 클래스 + 소스코드에서 추론한 것"의 카탈로그라서, **한 번도 안 건드려본 기능/화면에 있는 버그는 애초에 후보로도 안 올라온다.** 이걸 보완하기 위해 매 세션 Pass 1 시작 전에 짧게 가설 없는 탐색을 한다:

- 특정 기법을 검증하려는 목적 없이, 앱/API의 화면·기능을 최대한 넓게 훑어본다 (아직 techniques.md에 없는 기능 포함).
- "이게 취약점이다"라는 확신이 없어도, **설명이 안 되는 것**(예상과 다른 응답, 이상한 헤더/필드, 뜬금없는 지연, 접근 안 될 줄 알았는데 접근되는 화면 등)은 전부 기록한다.
- 이렇게 발견된 이상 징후는 바로 아래 "즉시 반영" 규칙에 따라 techniques.md에 새 항목으로 추가한다. Round 종료를 기다리지 않는다.

## 0.7 세션 스코프 선언 — 사람이 먼저 정함

techniques.md에 뭐가 몇 순위로 적혀있든, **이번 세션에 뭘 우선할지는 AI가 정하지 않는다.** 매 세션 Pass 1을 시작하기 전에 사람에게 열린 질문을 한다: "이번 세션엔 어느 쪽에 집중하고 싶으세요? (특정 기능/화면/비즈니스 영역, 또는 그냥 techniques.md 순서대로)"

- 사람이 특정 영역을 지정하면(예: "이번엔 결제 관련 로직만"), techniques.md 중 그 범위에 해당하는 항목만 추려서 1단계(태스크화)로 넘어간다.
- 사람이 "그냥 순서대로 해"라고 하면, techniques.md에 이미 정리된 순서(Priority 0 1~5 → Priority 1~4)를 기본값으로 쓰되, **이건 AI가 정적분석/추론으로 짠 잠정적 순서일 뿐 확정이 아니라는 점을 매번 다시 알린다.**
- 이미 이전 세션에서 스코프를 정해뒀다면 매번 처음부터 다시 물을 필요는 없지만, 새 Round로 넘어갈 때(3단계)는 항상 다시 확인한다.

## 1. 태스크 목록 구성

- `TaskList`로 기존 태스크 확인 — 이미 이번 세션에 만들어둔 techniques 태스크가 있으면 재사용, 없으면 새로 만든다.
- 0.7에서 정해진 스코프 안에서, `techniques.md`를 순서대로 읽고 각 기법 항목을 `TaskCreate`로 하나씩 등록한다. subject는 기법명, description은 해당 섹션의 "테스트 계획"/"성공 기준" 요약.
- 이미 `completed`로 표시된 항목은 다시 만들지 않는다 (중복 방지). `in_progress`/`pending`으로 남아있던 미완료 태스크가 있다면(이전 세션이 라운드 중간에 끝난 경우) 새 태스크를 만들기 전에 그것부터 이어서 처리한다.

## 2. Pass 실행 — Control 단위로 소비

블랑켓 승인("진행해" 등)이 성립한 범위 안에서, 태스크를 우선순위 순서대로 하나씩 꺼내 처리한다.

**제한적 병렬 실행**: 서로 다른 기능/엔드포인트를 건드리는 **완전히 독립적인** 기법들끼리는 최대 2~3개까지 동시에 진행해도 된다. 단, 같은 엔드포인트/기능을 대상으로 하는 여러 시도(파라미터만 다른 것 등)는 절대 동시에 보내지 않는다 — 같은 대상에 몰린 동시 요청은 "무제한 자동화"로 보이거나 rate-limit을 유발할 수 있다. 애매하면 순차 처리한다.

**배치 로깅**: 같은 계열의 시도(같은 엔드포인트에 파라미터만 바꿔가며 여러 번 시도하는 경우 등)는 Control 로그를 매번 새로 쓰지 않고, 하나의 Control 아래 결과를 표로 묶어서 `recon.md`에 기록해도 된다. 단 FACT는 시도별로 다 남긴다 (요약만 하고 개별 결과를 버리지 않는다).

1. 태스크를 `in_progress`로 표시.
2. AGENTS.md 형식대로 Control을 로그로 남긴다: Control ID, 목적, 명령, Target, 영향, 성공/실패 기준, Cleanup.
3. Control을 실행한다. (Target이 Safety 허용 범위를 벗어나거나 최초 Scope에 없던 새 범주면 개별 GO를 받는다.)
4. 결과를 `recon.md`에 FACT(관찰된 것: stdout/응답/상태코드)와 INFERENCE(해석)로 구분해 기록한다. 성공/실패/REJECTED/UNKNOWN 전부 남기고 삭제하지 않는다.
5. **이상 징후 즉시 반영 (Round 종료를 기다리지 않음)**: 이 FACT가 원래 노리던 것과 무관하게 예상과 다르거나 설명이 안 되면(뜬금없는 필드, 이상한 상태코드, 접근 안 돼야 할 게 되는 것 등), 그 즉시 `techniques.md`에 새 항목을 추가하고 `TaskCreate`로 태스크화한다. 몇 번째 Pass인지와 무관하게 발견 즉시 반영 — 카탈로그에 없던 취약점을 놓치지 않기 위한 안전장치.
6. 태스크를 `completed`로 표시.
7. **취약점이 실제로 확인되면**: 그 자리에서 스윕을 멈추지 말고 계속 진행하되, `finding-summary.md`에 1줄 요약 + CVSS/CWE 초안을 등록한다. 단, 상태는 "대기중"으로 — AI는 성공을 확정하지 않는다 (AGENTS.md "사람에게 남는 결정"). 그 취약점에 대해서는 이후 별도로 `retrospective/[VULN-ID]/verification.md`, `root-cause.md`를 채우는 재현검증 단계를 사람과 함께 진행한다.
8. **무진전 감지 (Pass 안에서의 조기 판단)**: 같은 계열의 기법(예: 같은 파라미터 변조 방식을 여러 엔드포인트에 반복 적용하는 것)을 연달아 3개 이상 시도했는데 계속 아무 신호(이상 징후·부분 성공 등)가 없으면, 남은 같은 계열 항목들을 전부 끝까지 순서대로 도는 대신 **우선순위를 낮춰 뒤로 미루고 다른 계열로 먼저 넘어간다.** 완전히 스킵하는 건 아니고, 이번 Pass에서 뒤로 미뤄지는 것뿐이다.

## 3. Pass 종료 — 전부 실패했을 때

techniques.md의 모든 태스크가 `completed`인데 확인된 취약점이 하나도 없다면, **곧바로 같은 시도를 반복하지 않는다.** (2단계 5번의 "이상 징후 즉시 반영"으로 이미 잡힌 것들은 이 시점엔 이미 techniques.md/태스크에 들어가 있으므로 여기서는 그 외의 것을 찾는다.)

**여기서 AI가 미리 확정한 계획을 예/아니오로만 승인받는 방식은 쓰지 않는다.** 그렇다고 AI가 아예 의견 없이 원본 데이터만 던지는 것도 아니다 — 기술적 판단(어떤 단서가 더 유력해 보이는지)은 AI가 내도 되고, 그게 이 스킬의 존재 이유(triage) 중 하나다. 대신 **비즈니스적/전략적 방향 선택권은 항상 사람에게 열어둔 채로** 다음 순서를 따른다:

1. `recon.md`를 다시 훑어서 눈에 띄는 raw FACT들(예상과 다른 응답, 에러 메시지, 힌트가 될 만한 헤더 등)을 **가공하지 않고 그대로** 먼저 보여준다.
2. 그 위에 AI의 기술적 triage 의견을 덧붙인다 — "이 중에서는 X가 기술적으로 가장 유력해 보입니다(이유: ...)" 처럼 **근거와 함께 의견을 내되, 단정하지 않는다.**
3. 열린 질문으로 마무리한다 — "이 방향으로 파볼까요, 아니면 다른 쪽이 더 궁금하세요?" (제 의견에 대해 예/아니오만 받는 게 아니라, 사람이 다른 방향으로 언제든 뒤집을 수 있다는 걸 매번 명시)
4. 사람이 AI 의견에 동의하든, 다른 방향을 지정하든, 그냥 "네가 알아서 정해"라고 위임하든 — 최종적으로 정해진 방향 안에서 구체적인 공격 기법을 작성해 `techniques.md`에 `## Round N`으로 추가한다. 각 항목에 어떤 FACT/누구의 판단(AI 의견 채택 or 사람 지정)에서 나왔는지 근거를 남긴다.
5. 새 공격 범주 추가이므로 AGENTS.md상 개별 GO가 필요 — Round N 태스크를 만들기 전에 "이 방향으로 만든 기법 목록이 이렇습니다, 진행할까요?" 최종 확인은 받되, 이건 방향 자체를 정하는 질문이 아니라 **이미 사람이 정한 방향을 AI가 제대로 구체화했는지 확인하는 것**이라는 점이 이전 버전과의 차이다.
6. 승인되면 1번(태스크 목록 구성)으로 돌아가 Round N 항목들을 태스크화하고 새 pass를 시작한다.

## 4. Round 상한

- 한 세션에서 **최대 3 pass**까지만 진행한다. 3 pass를 다 돌고도 못 찾았으면 자동으로 더 진행하지 않고, 지금까지의 결과를 정리해 사람에게 보고한 뒤 다음 세션에서 새 정찰 데이터를 갖고 다시 접근할지 논의한다.
- 세션 전체가 끝나거나 사용자가 "보고서"라고 입력하면 AGENTS.md의 "보고서 트리거" 형식(배경→접근방향→진행과정→결과→의미→다음단계)으로 `report.md`를 작성한다. 이 턴에서는 새 Control을 실행하지 않는다.

## 금지 사항 (이 스킬 안에서도 그대로 적용)

- `scope.md`가 PENDING이면 실제 Control 실행 금지.
- 동일 Control을 근거 없이 반복 실행 금지 — 반복하려면 왜 다시 실행해야 하는지(서버 재기동, 상태 변경 의심 등) 명시.
- 데이터 삭제/수정, 계정 탈취, 지속성 확보, DoS, 결제 시스템 직접 테스트 금지 (CLAUDE.md/scope.md 상속).
