Build Log

내가 Harness를 구축한 방법과 순서

강사 골격을 받은 시점부터, 자동 검사 도구를 만들고 두 번째 CVE로 재사용성을 검증하기까지 — 실제로 만든 순서 그대로.

01시작점 — 강사 골격 받기

빈 공책부터 만든 게 아니다. 강사가 이미 만들어둔 최소 골격(Repository)을 clone해서 내 계정의 새 Private Repository로 옮기는 것부터 시작했다. Fork를 쓰지 않은 이유는, Fork는 원본 저장소와의 연결 관계가 GitHub 안에 계속 남아서 "완전히 내 것"으로 독립시키기 어렵기 때문이다.

git clone (강사 저장소) → 새 폴더로 압축 해제 → git remote로 내 Private Repo 연결 → push

받은 골격 안에는 폴더 뼈대와 최소한의 안내 문서(README.md, AGENTS.md)만 있었고, 실제 내용은 거의 비어 있었다. 이걸 채워 넣는 게 이후 전체 과정이다.

02전체 구조 설계 — 두 영역으로 분리

제일 먼저 정한 원칙: "모든 CVE에 공통으로 적용되는 규칙"과 "CVE 하나하나의 실제 조사 결과"를 절대 같은 곳에 두지 않는다.

harness/ # 공통 규칙·절차·검증 도구 (CVE가 몇 개든 재사용) cves/ # CVE별 작업공간 └── CVE-2021-41773/ └── CVE-2021-43798/ scripts/ # harness/를 실제로 검사·실행해주는 도구 코드 tests/ # scripts/의 동작을 검증하는 자동 테스트

이렇게 나눠두면, 새 CVE를 하나 더 조사할 때 harness/는 전혀 안 건드리고 cves/ 아래에 폴더만 하나 추가하면 된다 — 실제로 두 번째 CVE(Grafana)를 조사할 때 정확히 이렇게 했다.

03공통 규칙 문서부터 채웠다

harness/ 폴더 자체를 채우기 전에, 저장소 최상위에 "이 안에서 어떻게 행동해야 하는지"를 정하는 계약 문서를 먼저 만들었다.

1AGENTS.md — AI와 나의 역할·승인 규칙
  • Day가 시작될 때(DAY 1 START 등) 뭘 먼저 확인해야 하는지
  • 실제 Control(실행)은 반드시 GO <control_id> 형식으로만 승인된다는 것
  • AI는 Scope·실행 권한·성공 여부·최종 결론을 스스로 확정하지 않는다는 것
2scope.md — 실행 범위와 STOP 조건
  • 허용 Target: 127.0.0.1/localhost와 이 저장소가 만든 격리 Docker Compose만
  • STOP 조건: 외부 IP·도메인, Credential 수집, 파괴적 동작, "알아서 해" 같은 모호한 승인
3harness/workflow.md — 전체 절차 한 줄 요약
CVE Intake → Source Map → Patch Diff → Root Cause → CWE → PLAN(Control Card) → HUMAN GO → RUN → CHECK(Same-Control) → Evidence Review → Report → Harness Diff
4harness/policies/invariants.md — 절대 안 바뀌는 규칙
  • 취약/조치 환경에 반드시 같은 Control·같은 요청을 적용한다(Same-Control)
  • 실행 환경(Docker 이미지)은 태그가 아니라 실제 실행 중인 컨테이너의 digest로 확인한다
  • Lab은 기본적으로 전부 차단(deny-by-default)하고, 필요한 경로만 최소로 연다

04D1 절차를 구축했다 — "조사"

첫 번째 CVE(Apache, CVE-2021-41773)를 실제로 조사하면서, 그 절차 자체를 재사용 가능한 형태로 다듬었다.

  1. intake.md — CVE ID, 제품, 취약/조치 버전 후보를 채워 넣는 기본 카드
  2. sources/source-map.md — 공식 Advisory·CVE Record·Repository만 출처로 인정하고, 각 출처가 어떤 Claim을 뒷받침하는지 표로 연결
  3. Claim 판정 — 조사 중 나온 주장 하나하나에 번호(CLAIM-001...)를 붙이고, ACCEPTED/CORRECTED/REJECTED/UNKNOWN 중 하나로 직접 판정
  4. analysis/root-cause.md, analysis/cwe.md — 코드 diff를 직접 읽고 FACT/INFERENCE/UNKNOWN을 구분해서 작성, 반증 조건도 같이 기록
  5. D1 Gate 확정 — 위 문서들을 전부 검토하고 확정해야 다음 단계로 넘어감
여기서 정한 규칙: FACT라고 쓰려면 반드시 [SRC-NNN] 같은 출처 표시가 있어야 하고, 없으면 INFERENCE나 UNKNOWN으로 남긴다. 이 규칙을 나중에 자동으로 검사하는 도구까지 만들게 된다(07절).

05D2 절차를 구축했다 — "재현"

조사만으로는 부족하다. 실제로 취약한 버전과 고쳐진 버전을 내 컴퓨터 안에 띄워서 눈으로 확인하는 단계를 만들었다.

Lab 설계 원칙

  • 이미지는 태그가 아니라 digest로 고정 — 나중에 태그가 다른 내용으로 바뀌어도 항상 같은 이미지를 쓴다는 보장
  • read_only: true + tmpfs — 컨테이너 안에서 정말 필요한 곳만 쓰기 허용
  • 127.0.0.1에만 포트를 열고, 실제 OS 파일 대신 Lab이 소유한 marker 파일로 성공 여부를 판별

Control Card와 승인 절차

실제로 뭔가 실행하기 전에는 항상 이 형식으로 먼저 제시하기로 정했다.

항목내용
목적왜 이 Control이 필요한지
명령실제로 실행할 명령
Target어디에 영향을 주는지 (127.0.0.1만)
영향뭐가 바뀌는지
성공/실패 기준뭐가 나오면 성공/실패인지
Cleanup끝나고 어떻게 원상복구하는지

이걸 보여준 뒤 정확히 GO <control_id> 형식으로 승인받은 뒤에만 실행했다. "진행해", "승인할게" 같은 표현은 형식이 안 맞으면 실행을 거부하도록 실제로 여러 번 테스트했다.

Same-Control 원칙 — 해시로 증명

취약한 버전과 고쳐진 버전에 완전히 똑같은 요청을 보냈다는 걸 증명하기 위해, 요청 내용·판정 기준을 각각 sha256으로 해시해서 두 Target에서 같은 값이 나오는지 대조하는 절차를 만들었다.

06D3 절차를 구축했다 — "정리"

  1. Evidence Review — 실행 결과(raw)를 내가 직접 검토해서 REVIEWED/report_eligible로 승인해야 보고서에 인용 가능
  2. Masked Evidence — raw는 그대로 보존하고, 강의·제출용으로 민감 정보를 가릴 사본을 별도로 만듦(이번엔 원래 민감 정보가 없어서 내용은 동일했음)
  3. 보고서 작성 규칙 — 승인된 Evidence만 인용하고, 성공/실패 주장마다 [evidence:ID] 태그를 반드시 붙인다
  4. retrospective/reuse-check.md — 이번 CVE를 조사하며 harness 자체에서 발견한 문제를 "실패 Ref / 원인 / 변경 위치 / 재실행 결과 / 다음 CVE 재사용 영향" 형식으로 기록

07자동 검사 도구를 만들었다

규칙을 문서로만 적어두면 사람이 매번 눈으로 확인해야 한다. 그래서 scripts/lib/checks.mjs에 D1/D2/D3 각 단계가 실제로 규칙을 지켰는지 자동으로 검사하는 함수를 만들었다.

단계자동으로 검사하는 것
D1Scope에 STOP 조건이 있는지, FACT 문장마다 출처가 있는지, Intake가 비어있지 않은지
D2Target이 loopback인지, GO 승인이 있는지, digest가 고정돼 있는지, Cleanup이 정의됐는지
D3취약/조치 Observation의 해시가 서로 같은지(Same-Control), 보고서가 인용한 Evidence가 실제로 승인됐는지
npm run check -- D1 CVE-2021-41773

이 명령 하나로 "지금 이 CVE의 D1 산출물이 규칙을 지켰는지"를 즉시 확인할 수 있게 됐다. 통과하면 GO, 문제가 있으면 REVISE 또는 STOP이 뜬다.

08재사용성을 실제로 검증했다

도구를 "만들었다"는 주장만으로는 부족하다고 생각해서, 전혀 다른 소프트웨어의 다른 취약점(Grafana, CVE-2021-43798)에 harness/ 폴더를 하나도 안 건드리고 그대로 적용해봤다.

npm run new:cve -- CVE-2021-43798 # 표준 폴더 구조 자동 생성

같은 D1→D2→D3 순서, 같은 Control Card 형식, 같은 자동 검사 명령이 그대로 먹혔다 — 이게 "이 harness가 재사용 가능한 도구"라는 걸 증명하는 방법이라고 생각했다.
