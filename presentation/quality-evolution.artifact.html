v1.3 · 원래는 출처 검사가 작동 안 했다

"출처 없는 FACT 방지" 문구는 있었는데, 검사기는 없었다

보고서에는 "자동 검증기로 확인된다"고 적혀 있었지만, 실제 코드를 다시 열어보니 조용히 무력화돼 있었다.

발견된 문제 (before)

검사 코드가 line.trim().startsWith("FACT:")로 줄을 찾았는데, 실제 문서는 전부 마크다운 bullet(- FACT: ...)로 시작 — "- FACT:".startsWith("FACT:")는 항상 false.

게다가 이 검사는 cwe.md에는 아예 호출되지도 않았음. 정규식 /\[SRC-\d+\]/도 [SRC-003a] 같은 접미사 붙은 참조는 못 잡음.

결과: 만들어진 이후 실제 파일에서 단 한 번도 작동한 적이 없었다

수정 (after)

줄 매칭을 /^-?\s*FACT:/로, 출처 정규식을 /\[(SRC|CLAIM|CLM)-\d+[a-zA-Z]?\]/로 확장. checkD1()에 cwe.md 검사 호출도 추가.

검증: 출처 없는 FACT 줄을 일부러 추가해보니 정확히 REVISE로 잡히고, 원상복구하면 다시 GO로 돌아옴을 확인.

이제 root-cause.md·cwe.md 둘 다 FACT마다 출처가 강제됨

v1.4 · 원래는 접근 실패 기록이 없었다

우회 경로로 출처를 구했는데, 그 사실 자체가 문서에 없었다

cve.org의 공식 CVE Record는 동적 렌더링 페이지라 정적 Fetch로는 본문이 비어 있었다. 대체 경로로 성공했지만, 처음엔 이 우회 과정이 어디에도 기록되지 않았다.

beforesources/source-map.md

SRC-002 = CVEProject 공식 저장소 raw JSON

→ 왜 cve.org 원본이 아니라 raw JSON을 썼는지는 기록 없음

aftersources/source-map.md

추가된 절

시도: cve.org/CVERecord?id=... 직접 Fetch → 실패(클라이언트 사이드 렌더링, 본문 미포함)

대체 경로: 같은 CNA가 관리하는 CVEProject/cvelistV5 raw JSON → 성공, SRC-002로 채택

v1.5 · 원래는 사람이 눈으로 판단했다

curl 결과를 읽고 "성공/실패"를 사람이 정했다

같은 검사를 두 이름(VULNERABLE_MATCH/PATCHED_BLOCK vs TRAVERSAL_MARKER_CHECK)으로 부르고 있었고, "무엇을 검사하면 통과인지"가 코드로 존재하지 않았다.

before

스크립트는 curl 응답(HTTP 코드, 본문)을 출력만 하고, marker 문자열이 실제로 있는지는 사람이 화면을 보고 판단.

after

스크립트가 grep으로 marker 유무를 직접 확인해 자동 출력:

MATCHER=TRAVERSAL_MARKER_CHECK LABEL=VULNERABLE_MATCH VERDICT=MATCH

v1.6 · 원래는 해시를 6번 손으로 옮겨 적었다

같은 값을 여섯 파일에 중복 입력 — 대조하는 코드는 없었다

input_sha256/request_sha256/criteria_sha256이 vulnerable.json, patched.json, observation.json, observation-patched.json, evidence/index.json(2건) 총 6곳에 손으로 중복 입력돼 있었다.

수정

checkExecutionConsistency()를 추가해 checkD3()에서 존재하는 Observation류 파일들 사이 세 해시값이 전부 같은지 자동 대조.

검증: input_sha256 앞 8자를 일부러 deadbeef로 바꿔보니 REVISE execution consistency: input_sha256 differs across ...로 정확히 잡힘.

종합

"검사기가 있다"와 "검사기가 실제로 작동한다"는 다르다

발견 패턴

  • 문서에 "자동 검증됨"이라 적혀 있어도 코드를 다시 열어봐야 함(v1.3)
  • 우회/대체 경로를 썼다는 사실 자체가 근거임 — 기록 안 하면 사라짐(v1.4)
  • 사람이 눈으로 판단하는 단계는 재현 불가능한 판정임(v1.5)
  • 같은 값을 여러 파일에 손으로 옮기면 반드시 어긋난다(v1.6)

모든 수정에 공통된 절차

  • 일부러 틀린 값/누락을 넣어 검사기가 실제로 잡는지 확인
  • 원상복구 후 다시 GO로 돌아오는지 재확인
  • npm test 회귀(34/34)로 기존 CVE에 영향 없는지 확인
