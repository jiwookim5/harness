보안 초심자의 기록

내 손으로 취약점 분석 도구를 만들고, 실제로 써본 하루

보안 취약점(CVE)을 조사할 때 "AI가 그럴듯하게 말한 것"과 "실제로 확인된 것"을 구분하지 못하면 아무 의미가 없다. 그래서 오늘은 이 둘을 억지로라도 분리해주는 나만의 조사 도구(harness)를 만들고, 그 도구로 진짜 취약점 두 개를 직접 조사해봤다. 이 글은 그 하루를 순서대로 정리한 것이다.

시작하며

왜 이런 도구가 필요했나

보안 취약점을 조사할 때 제일 위험한 건, 그럴듯하게 들리는 설명을 그냥 믿어버리는 것이다. "이 버전에 이런 문제가 있대"라는 말을 듣고 그대로 믿는 것과, 그걸 직접 실행해서 눈으로 확인하는 것 사이에는 큰 차이가 있다.

비유로 보면

소문으로 들은 이야기와, 내가 두 눈으로 직접 본 것은 다르다. 재판에서 "카더라"는 증거로 안 쳐주는 것처럼, 여기서도 "AI가 그렇게 말했다"는 증거가 아니다. 실제로 재현해서 관찰한 결과만 증거로 인정한다는 규칙을 처음부터 정해두고 시작했다.

그래서 도구 자체에 몇 가지 규칙을 못박아뒀다. 실행은 반드시 정확한 승인 문구 (GO <control_id>)를 받은 뒤에만 하고, 확실한 사실에는 항상 출처를 달고, 확인 안 된 건 그냥 "모름"으로 남겨두고 넘어가지 않는다는 것.

1장

이 도구를 실제로 어떻게 만들었나

맨 처음부터 혼자 만든 건 아니었다. 강사가 기본 뼈대(빈 폴더 구조, 최소한의 규칙 문서)를 미리 만들어서 나눠줬고, 나는 그걸 내 저장소로 가져와서 필요한 내용을 직접 채워 넣고 확장하는 방식으로 만들었다.

폴더를 두 종류로 나눴다

제일 먼저 정한 건 "공통 규칙"과 "사례별 결과물"을 절대 섞지 않는다는 원칙이었다.

폴더담는 것
harness/모든 취약점 조사에 공통으로 적용되는 규칙, 절차, 자동 검사 도구
cves/CVE-번호/취약점 하나하나의 실제 조사 기록·실행 결과·보고서
비유로 보면

요리 학원의 "조리 원칙과 위생 수칙"(공통 규칙)과, 그날그날 만든 요리 하나하나의 "레시피 카드"(사례별 결과물)를 따로 관리하는 것과 같다. 원칙은 요리가 바뀌어도 그대로 쓰고, 레시피 카드만 요리마다 새로 만든다.

공통 규칙 안에 정확히 뭘 넣었나

  • 순서조사 절차를 아홉 단계로 못박았다: 공식 자료 조사 → 수정 전/후 코드 비교 → 원인 분석 → 취약점 분류 → 실행 계획 세우기 → 사람 승인 받기 → 실제 실행 → 재현 결과 비교 → 보고서 작성
  • 역할어떤 결정은 절대 AI가 혼자 내리지 못하게 정해뒀다 — 조사 범위 승인, 실행 승인, 성공 여부 확정, 최종 결론 확정은 전부 나만 할 수 있다
  • 안전실행 대상은 내 컴퓨터 안(localhost)으로만 한정했고, "진행해", "알아서 해" 같은 애매한 말은 승인으로 인정하지 않고, 정확한 형식 (GO CTL-xxx)으로만 승인이 되게 정했다
  • 근거 등급모든 문장을 "확실한 사실(출처 있음)" / "추론(근거로 유추했지만 확실친 않음)" / "아직 모름" 세 등급으로 나누고, 셋을 절대 섞지 않기로 했다
  • 자동 검사이 규칙들을 실제로 지켰는지 사람이 매번 눈으로 확인하는 대신, 프로그램이 자동으로 검사해주는 도구를 같이 만들었다

취약점 하나를 조사할 때마다 폴더 하나씩 쌓인다

새 취약점을 조사할 때마다 cves/CVE-번호/ 아래에 같은 모양의 하위 폴더가 자동으로 만들어지도록 했다 — 조사 기록을 넣는 곳, 실행 환경을 넣는 곳, 실제 실행 결과(증거)를 넣는 곳, 보고서를 넣는 곳이 항상 똑같은 자리에 있다. 그래서 취약점이 몇 개로 늘어나도 "이번엔 어디에 뭘 넣어야 하지"를 매번 새로 고민할 필요가 없었다.

가장 신경 쓴 부분

만들면서 제일 신경 쓴 건 "사람이 뭘 승인하는지"를 흐릿하게 두지 않는 거였다. 실행 전에는 항상 무엇을, 어떤 대상에, 어떤 영향으로, 어떻게 되돌리는지(Cleanup) 먼저 보여주고, 그걸 보고 나서 정확한 형식으로 승인해야만 다음 단계로 넘어가게 만들었다. 이 원칙 덕분에 나중에 "이걸 진짜 내가 승인한 게 맞나"를 헷갈릴 일이 없었다.

2장

연습 대상으로 첫 번째 취약점을 조사했다

첫 대상은 Apache라는 아주 널리 쓰이는 웹 서버 소프트웨어의 취약점(CVE-2021-41773)이었다. "경로 순회(Path Traversal)"라고 부르는 종류인데, 쉽게 말하면 원래는 못 보게 막아둔 파일에, 요청 주소를 교묘하게 만들어서 접근할 수 있게 되는 문제다.

어떻게 조사했나

순서는 이랬다: 회사(Apache)가 공식적으로 낸 발표문을 먼저 읽고 → 문제가 있던 버전과 고쳐진 버전의 실제 코드를 받아서 직접 비교(diff)하고 → 그 차이를 바탕으로 "왜 이 문제가 생겼는지" 정리하고 → 마지막으로 내 컴퓨터 안에 두 버전을 각각 띄워서 진짜로 재현되는지 직접 확인했다.

결과

버전상황결과
문제 있는 버전보호 설정 없는 경우파일 노출됨 (재현 성공)
고쳐진 버전동일 조건차단됨

공식 문서의 설명이 실제 동작과 정확히 일치한다는 걸 내 손으로 확인한 첫 사례였다.

3장

같은 도구로, 완전히 다른 취약점을 조사했다

도구를 한 번 쓰고 버릴 거면 만들 이유가 없다. 그래서 이번엔 전혀 다른 소프트웨어(Grafana, 데이터 시각화 대시보드 도구)의 다른 취약점 (CVE-2021-43798)에 같은 도구를 그대로 적용해봤다.

비유로 보면

레시피가 좋은 레시피라면, 재료만 바꿔서 다른 요리에도 써먹을 수 있어야 한다. "이 재료 한정으로만 되는 레시피"는 사실 좋은 레시피가 아니다.

결과

이번엔 첫 번째 취약점과 달리 별도의 안전하지 않은 설정 없이, 그냥 기본 설치 상태 그대로 문제가 재현됐다 — 훨씬 더 위험한 종류였다는 뜻이다. 같은 도구, 같은 절차인데도 다른 소프트웨어에 바로 적용됐다는 게 이 도구가 "재사용 가능하다"는 증거였다.

4장

도구를 쓰다가, 도구 자체의 문제를 발견했다

취약점을 두 개 조사하고 나니, 도구 자체에도 손볼 곳이 여럿 보였다. 만들 때는 몰랐는데 실제로 써봐야만 드러나는 문제들이었다.

  • 1내 컴퓨터(macOS)의 기본 프로그램이 너무 오래된 버전이라 스크립트가 실행되자마자 멈췄다
  • 2비밀번호도 아닌 파일이 "비밀번호 방지 규칙"에 걸려서 저장이 안 됐다
  • 3검사 도구가 처음 만든 CVE 이름 하나만 볼 줄 알아서, 두 번째 취약점은 검사가 아예 안 됐다
  • 4"근거 없이 확정하지 마라"는 검사 도구가 사실 한 번도 제대로 작동한 적이 없었다
  • 5"성공/실패"를 사람이 눈으로 읽고 판단하고 있었다 — 코드가 확인한 게 아니었다
  • 6같은 값을 여러 파일에 손으로 반복 입력하다 보니, 서로 다른 값이 들어가도 아무도 몰랐다

여섯 개 다 찾아서 고쳤고, 특히 5번과 6번은 서로 원인과 결과 관계였다 — 6번(값을 손으로 여러 번 입력)이 바로 5번(판정 이름이 서로 안 맞았던 것)이 아무도 모르게 생길 수 있었던 진짜 이유였다.

(여섯 개를 하나씩 자세히 풀어 쓴 글은 따로 있다 — 이 글은 오늘 하루 전체를 훑는 요약이라 여기선 목록으로만 남긴다.)

오늘 배운 것

도구는 한 번 만들면 끝나는 게 아니었다. 처음 만든 도구가 완벽했던 게 아니라, 실제로 두 번째 대상에 써봐야만 첫 번째 대상만으로는 절대 안 보였을 문제들이 드러났다. 그리고 그 문제들 중 몇 개는 소리 없이 조용히 작동을 안 하고 있었다 — "에러가 없다"는 게 "제대로 검사됐다"는 뜻이 아니라는 걸 오늘 제일 크게 배웠다.
